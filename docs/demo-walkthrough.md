## Global Constraints

กฎเหล่านี้คัดมาจากกฎที่เขียนไว้ในโค้ดเองหรือใน AGENTS.md และผูกกับ **ทุกงาน** ใน Phase 2

1. `packages/core` ห้าม import framework ใดๆ (AGENTS.md กฎเหล็กข้อ 1) แผนนี้ไม่แตะ core อยู่แล้ว
2. เงินเป็นจำนวนเต็มหน่วยสตางค์เสมอ ใช้ชนิด `Satang` ห้ามใช้ทศนิยมกับเงินทุกกรณี (กฎเหล็กข้อ 3) แปลงเป็นบาทตอนแสดงผลเท่านั้น
3. การซ่อนต้นทุนบังคับที่ API ผ่าน `ok()` กับ `FIELD_POLICIES` ใน `packages/core/src/rbac.ts` (กฎเหล็กข้อ 4)
   ถ้าเพิ่ม field ที่มีต้นทุน ต้องใส่คีย์เข้า `COST_KEYS` และกำกับ `/** cost field */` ในไฟล์ contract มิฉะนั้น `contract-audit.test.ts` จะตก
   การซ่อนใน React เป็นแค่เครื่องสำอาง ไม่ใช่ความปลอดภัย
4. FIFO ต้องรันในทรานแซกชันเดียว อ่านล็อตด้วย `SELECT ... FOR UPDATE` (กฎเหล็กข้อ 5) `POST /demo/reset` ก็ต้องอยู่ในทรานแซกชันเดียวเช่นกัน
5. Import ไฟล์เดิมซ้ำต้องไม่ตัดสต็อกซ้ำ ค้ำด้วย unique index `orders_channel_external_uq` บน `(channel_id, external_order_id)` (กฎเหล็กข้อ 6)
6. การคืนของต้องคืนที่ **ต้นทุนเดิม** ผ่าน `restoreFifo` ที่รับ `LotConsumption[]` ของการขายเดิม ไม่ใช่ราคาทุนวันนี้ (กฎเหล็กข้อ 7)
7. ทุกคำสั่งอ่านเขียนข้อมูลต้องกรองด้วย `orgId` เสมอ ทุก repository ในโค้ดปัจจุบันรับ `orgId` เป็นพารามิเตอร์บังคับ งานใหม่ต้องทำเหมือนกัน
8. TypeScript strict เปิดทุก flag ใช้ `import type` เสมอ (เปิด `verbatimModuleSyntax`) ห้าม `any` ห้าม `!` (เปิด `noUncheckedIndexedAccess`)
9. ไฟล์ตั้งชื่อแบบ `kebab-case.ts` ชนิดและ interface เป็น `PascalCase` ฟังก์ชันและตัวแปรเป็น `camelCase`
10. คอมเมนต์เป็นภาษาอังกฤษและต้องอธิบาย **ทำไม** ไม่ใช่ **ทำอะไร** ข้อความบนจอเป็นภาษาไทย
11. โยนได้เฉพาะ `StockHubError` หรือคลาสลูก และต้องมี `code` ที่คงที่ เพราะ frontend อ่าน `code` ไม่ได้อ่านข้อความ
12. หน้าจอทุกหน้าต้องมีครบ 3 สถานะ กำลังโหลด ว่างเปล่า และผิดพลาด ตัวเลขต้นทุนทุกตัวต้องครอบด้วย `<CostValue>`
13. ห้าม commit ไฟล์ export ของลูกค้าจริง ข้อมูลผู้ซื้อในไฟล์ตัวอย่างต้องเป็นชื่อสมมติทั้งหมด (AGENTS.md ข้อ 8)
14. หัวข้อ commit ยาวไม่เกินประมาณ 50 ตัวอักษร รูปประโยคคำสั่ง หนึ่ง commit ทำหนึ่งเรื่อง ห้ามใส่ชื่อ AI เป็นผู้ร่วมเขียน
15. ในไฟล์ Markdown เขียนหนึ่งประโยคต่อหนึ่งบรรทัด และห้ามใช้อักขระขีดยาว ใช้ขีดสั้นแทน

SOURCE: `apps/web/src/lib/demo-identity.ts:22-38` (ตัดย่อหน้าออกเพื่อให้อ่านง่าย ไม่ใช่การคัดลอกคำต่อคำ)

`tour-provider.tsx` ต้องทำแบบเดียวกัน คือมีโมดูลเก็บค่าปัจจุบัน 1 ตัว และ provider เป็นตัวเดียวที่เขียน `localStorage`

### รูปแบบอ่าน env ของ browser bundle

SOURCE: `apps/web/src/lib/config.ts:8-17`

```ts
export const API_URL = (process.env.NEXT_PUBLIC_API_URL ?? 'http://localhost:8787').replace(/\/$/, '');

## A. Persona และเรื่องเล่า

### ร้าน

**ร้านเกษตรรุ่งเรือง** (`organizations.name` ใน seed, id `0a000000-0000-4000-8000-000000000001`, เขตเวลา Asia/Bangkok)

### เรื่องเล่า: หนึ่งวันทำงานของร้าน

เช้าวันนี้ของปุ๋ยยูเรียเพิ่งเข้า 2 รอบ คนละราคา
สายๆ พนักงานโหลดไฟล์ออเดอร์จาก Shopee, Lazada และ TikTok Shop มาตัดสต็อก
ระหว่างนั้นเจอ SKU ที่ระบบยังไม่รู้จัก เจอไฟล์ที่มีแถวพิมพ์ผิด และเผลอ import ไฟล์เดิมซ้ำ
บ่ายมีสหกรณ์มารับปุ๋ย 100 กระสอบ ต้องออกบิลขายส่งและพิมพ์ใบส่งของ
เย็นมีลูกค้าเดินเข้าร้านซื้อปุ๋ย 2 กระสอบแล้วเปลี่ยนใจ ต้องยกเลิกบิล
ปิดร้าน เจ้าของเปิดดูว่าวันนี้ขายได้เท่าไร กำไรเท่าไร แล้วลองสลับเป็นมุมมองพนักงานขายเพื่อยืนยันว่าลูกน้องมองไม่เห็นต้นทุน

### E.1 รูปแบบที่เลือก

เลือก **แผงด้านขวาแบบรายการขั้นตอน (side panel checklist) + ไฮไลต์ปุ่มเป้าหมาย (spotlight) + การ์ดสรุปหลัง action (Data Flow card)**

เหตุผลที่ไม่เลือกแบบ modal ครอบทีละขั้น: Demo นี้ต้องให้ client เห็น **ตัวเลขบนหน้าจอเปลี่ยน** ซึ่ง modal จะบัง
แผงด้านขวาอยู่คู่กับหน้าจริงตลอด client จึงเห็นทั้งคำอธิบายและผลลัพธ์พร้อมกัน

**ข้อจำกัดของโครงหน้าจอที่มีอยู่** `layout.tsx` ใช้ `h-screen` กับ `overflow-hidden` ดังนั้นแผงด้านขวาต้องเป็นคอลัมน์ที่สามของ flex เดิม และต้องมี `overflow-y-auto` ของตัวเอง ห้ามใช้ `position: fixed` ทับ
แผงต้องมีคลาส `print:hidden` ด้วย เพราะขั้นที่ 14 สั่งพิมพ์ใบส่งของ ถ้าไม่ใส่ แผงทัวร์จะติดไปบนกระดาษ
และวงแหวนไฮไลต์ต้องคำนวณตำแหน่งใหม่เมื่อหน้าเลื่อนหรือเปลี่ยนขนาด (ผูก listener กับ `scroll` และ `resize`) มิฉะนั้นวงแหวนจะลอยผิดที่ทันทีที่ผู้ใช้เลื่อนจอ

```
+--------------------------------------------------+-------------------------+
|  แถบบน: โลโก้ | ตำแหน่งงาน [สมชาย เจ้าของร้าน v]   |  แผงทัวร์               |
+--------+-----------------------------------------|  ขั้นที่ 12 จาก 20       |
| เมนู   |                                          |  [====        ] 60%     |
| ข้าง   |   เนื้อหาหน้าจริง                          |                         |
|        |   (ปุ่มเป้าหมายมีวงแหวนเรืองแสงล้อม)        |  เปิดบิลขายส่ง            |
|        |                                          |  เลือกลูกค้าแล้วราคา      |

|        |                                          |                         |

### E.3 สถานะที่เก็บ

เก็บใน `localStorage` คีย์ `stockhub.tour.state` เป็น JSON รูปแบบนี้

```ts
interface TourState {
  /** ขั้นที่กำลังทำอยู่ 1 ถึง 20; 0 = ยังไม่เริ่ม */
  currentStep: number;
  /** ขั้นที่ทำสำเร็จแล้ว */
  completedSteps: number[];
  /** ผู้ใช้กดปิดทัวร์ไปเอง */
  dismissed: boolean;
  /** id ที่ระบบสร้างระหว่างทัวร์ เพื่อให้ลิงก์ "ไปดูหน้าที่กระทบ" ชี้ถูกใบ */
  refs: { ureaVariantId?: string; lastImportId?: string; wholesaleOrderId?: string; posOrderId?: string };
}
```

`refs` จำเป็นเพราะ id ของบิลและไฟล์ import ถูกสร้างตอนรันไทม์ ไม่ใช่ค่าคงที่ใน seed
ถ้าไม่เก็บไว้ ลิงก์ "ไปดูหน้าที่กระทบ" จะไม่รู้ว่าต้องไปใบไหน

ใช้ `localStorage` แบบเดียวกับที่ role switcher ใช้อยู่แล้ว (`stockhub.demo.role` ใน `lib/demo-identity.ts:24`) เพื่อไม่เพิ่มแนวคิดใหม่

### E.4 วิธีไฮไลต์ element

ทุก element เป้าหมายติด attribute `data-tour-id="receive-submit"` เป็นต้น
`tour-spotlight.tsx` หาตัวนั้นด้วย `document.querySelector` แล้วอ่าน `getBoundingClientRect()` มาวาดกรอบ `position: fixed` ทับ
ไม่มีการแก้ DOM ของหน้าจริง และไม่บล็อกการคลิก ผู้ใช้กดอย่างอื่นได้ตลอด

ถ้าหา element ไม่เจอ (เช่นหน้ายังโหลดไม่เสร็จ) ให้ไม่วาดอะไรเลยและไม่ throw

### E.6 เมื่อผู้ใช้ออกนอกเส้นทาง

**ไม่บังคับทาง** ตามโจทย์
ถ้าผู้ใช้อยู่คนละหน้ากับขั้นปัจจุบัน แผงทัวร์แสดงข้อความเดียว พร้อมปุ่มกลับ

> ตอนนี้คุณอยู่หน้า "ความเคลื่อนไหวสต็อก" ขั้นที่ 12 อยู่ที่หน้า "เปิดบิล"
> [ไปหน้านั้น] [ทำขั้นนี้ทีหลัง]

ถ้าผู้ใช้ทำ action ของขั้นอื่นที่ยังไม่ถึง ให้ติ๊กขั้นนั้นว่าสำเร็จแล้วเดินหน้าไปขั้นถัดไปที่ยังไม่สำเร็จ
ไม่มีการปิดปุ่มหรือกันไม่ให้กดอะไรทั้งสิ้น

### E.7 การ์ด Data Flow

โผล่หลังทุก action ที่เขียนข้อมูล (ขั้นที่ 2, 3, 5, 6, 7, 8, 9, 10, 12, 15, 16, 20)
อยู่ได้จนกว่าจะกดปิดหรือเปลี่ยนหน้า มี 4 ช่องตายตัว

```
+--------------------------------------------------------------+
| ทำอะไร      บันทึกรับปุ๋ยยูเรีย 50 กระสอบ ทุน 1,085.00           |
| เห็นอะไร     ยูเรีย 60 -> 110 กระสอบ                            |
|             มูลค่าสต็อก 439,245.00 -> 493,495.00               |
| ข้อมูลไปไหน  ความเคลื่อนไหวสต็อก 1 รายการ, ล็อตต้นทุน 1 ล็อต      |
| กระทบหน้าไหน [ภาพรวม] [สต็อกสินค้า] [ความเคลื่อนไหวสต็อก]         |
+--------------------------------------------------------------+
```

ตัวเลข before และ after **ต้องไม่ hardcode**
`use-tour-step.ts` อ่านค่า Dashboard ผ่าน `api.getDashboardSummary()` **ก่อน** ทำ action เก็บไว้ แล้วอ่านอีกครั้ง **หลัง** ทำ action แล้วแสดงผลต่าง
ตัวเลขในแผนหัวข้อ C ใช้เป็น **ค่าคาดหวังของเทส** (งานที่ 14) ไม่ใช่ค่าที่โปรแกรมแสดง

**ข้อจำกัดที่ต้องรู้:** `GET /dashboard/summary` ให้แค่ยอดรวมทั้งร้าน ไม่ได้ให้ยอดรายตัวสินค้า
ตาราง C บางขั้นสัญญาตัวเลขรายตัว เช่น "จอบ 100 เป็น 98" ซึ่งต้องอ่านจาก `GET /inventory` หรือ `GET /inventory/:id` เพิ่ม
การ์ดจึงต้องเรียก 2 แหล่ง คือยอดรวมจาก Dashboard และรายตัวจาก inventory ของ SKU ที่เกี่ยวข้องกับขั้นนั้น
รายชื่อ SKU ที่ต้องอ่านของแต่ละขั้นอยู่ใน `tour-steps.ts`

### E.8 flag เปิดปิด

ใช้ตัวแปรใหม่ชื่อ **`NEXT_PUBLIC_GUIDED_DEMO`** ค่าตั้งต้น `false`
Guided Tour ทำงานเมื่อ `NEXT_PUBLIC_GUIDED_DEMO === 'true'` เท่านั้น

**ห้ามใช้ `NEXT_PUBLIC_DEMO_MODE` ที่มีอยู่แล้ว** เพราะตัวนั้นแปลว่า "ตอบทุก request ด้วย mock โดยไม่ต้องมี backend" (`apps/web/src/lib/config.ts:17` และ `api-core.ts:25-29`) และค่าตั้งต้นของมันคือ **เปิด**
ถ้าเอามาใช้ซ้ำ Demo จะโชว์ตัวเลข mock ซึ่งผิดกฎข้อ 5 ของโจทย์ทันที

Guided Tour ต้องรันคู่กับ `NEXT_PUBLIC_DEMO_MODE=false` เสมอ
ถ้าตรวจพบว่าเปิดทั้งคู่ ให้แผงทัวร์ขึ้นแถบแดงว่า "กำลังใช้ข้อมูลจำลอง ตัวเลขไม่ใช่ของจริง" แทนที่จะเดินทัวร์ต่อเงียบๆ

เมื่อ `NEXT_PUBLIC_GUIDED_DEMO` ไม่ใช่ `'true'`:
- `layout.tsx` ไม่ render `TourProvider` และ `TourPanel` เลย
- ปุ่ม "ใช้ไฟล์ตัวอย่าง" และปุ่ม "รีเซ็ต Demo" ไม่ปรากฏ
- `POST /api/v1/demo/reset` ตอบ **404** (ดู H.2)

- ทั้ง 3 แพลตฟอร์มมีคอลัมน์ required 5 และ unique 3 สูตรคะแนนคือ `0.55 x สัดส่วน required + 0.45 x สัดส่วน unique`
  ไฟล์ตัวอย่างต้องมี required ครบ 5 และ unique **พอดี 1 คอลัมน์** จึงได้ **0.70** พอดี (ถ้ามี 2 จะได้ 0.85 ถ้ามี 3 จะได้ 1.00)
  สำหรับไฟล์ Shopee ห้ามใส่คอลัมน์ `ชื่อตัวเลือก` และ `ชื่อผู้ใช้ (ผู้ซื้อ)` เพราะทั้งคู่เป็น unique header (`packages/adapters/src/shopee/columns.ts:62-71`)
  ถ้าจะใส่ชื่อผู้ซื้อ ต้องแก้ตัวเลข 0.70 ในขั้นที่ 4 และในงานที่ 4 ให้เป็น 0.85
  (ค่าเกณฑ์ `DETECTION_THRESHOLD` อยู่ที่ `packages/adapters/src/registry.ts:66` ส่วนสูตรคิดคะแนนอยู่ที่ `packages/adapters/src/shared/header-match.ts:140-170`)
- **ทั้ง 3 ไฟล์ต้องมีคอลัมน์วันที่** ไม่งั้นทั้งออเดอร์ตายด้วย `bad_date`
  รวมถึง Lazada ด้วย ซึ่ง `orderedAt` อยู่ในรายการ required ของ `LAZADA_SIGNATURE` และ adapter จะ `continue` ทิ้งทั้งออเดอร์ถ้าแปลงวันที่ไม่ได้
  ถ้าไฟล์ Lazada ไม่มี `createTime` ขั้นที่ 7 จะได้ 0 ออเดอร์ และลำดับตัวเลขจะค้างที่ 2,919 แทนที่จะเป็น 2,906
- ข้อมูลผู้ซื้อทุกช่องเป็นชื่อสมมติ ห้ามมีข้อมูลลูกค้าจริงเด็ดขาด ตาม AGENTS.md หัวข้อ 8
- ไฟล์ทั้ง 4 ต้องผ่าน adapter **ตัวเดียวกัน** กับไฟล์ที่ผู้ใช้อัปโหลดเอง ไม่มีทางลัด

## K. โจทย์ที่ได้รับ

**คำเตือนสำหรับผู้ตรวจแผน:** ส่วนที่อยู่ในเครื่องหมายคำพูดข้างล่างคือข้อความที่คัดลอกมาตรงตัว
ส่วนที่อยู่ใต้หัวข้อ "ข้อกำหนดอื่นที่ได้รับในบทสนทนาเดียวกัน" เป็นการ **สรุปความ** ไม่ใช่การคัดลอกคำต่อคำ
โจทย์มาจากบทสนทนา ไม่มีไฟล์ spec ดังนั้นถ้าข้อกำหนดใดหล่นหายไปก่อนถึงหัวข้อนี้ ผู้ตรวจแผนจะมองไม่เห็น
ถ้าตรวจพบว่าสรุปตกหล่น โปรดทักท้วงที่ผู้เขียนแผนโดยตรง

> ออกแบบและสร้าง "Guided Demo Walkthrough" สำหรับระบบสต็อกสินค้าเกษตร (FIFO + Import ออเดอร์ 3 แพลตฟอร์ม + ระดับราคา + สิทธิ์ซ่อนต้นทุน)
> เพื่อให้ client ที่เห็นระบบครั้งแรกเข้าใจภายใน 15 นาทีว่า ทำ action นี้แล้วเห็นผลอะไร ข้อมูลวิ่งไปไหน และไปกระทบ feature ใด
> โดย client ไม่ต้องเตรียมไฟล์ ข้อมูล หรือ asset ใดๆ เอง ทุกอย่างต้องมีอยู่ในระบบแล้ว

หลักการออกแบบที่ต้องยึด 5 ข้อ

1. Zero-asset ไฟล์ export ตัวอย่างของทั้ง 3 แพลตฟอร์มต้องถูก bundle ไว้ในระบบ กดปุ่มเดียวเพื่อ "ใช้ไฟล์ตัวอย่าง" ได้ แต่ต้องยังอัปโหลดไฟล์จริงได้
2. ทุก step ต้องตอบ 4 อย่างบนหน้าจอ ทำอะไร เห็นอะไร (before/after) ข้อมูลวิ่งไปไหน ไปกระทบหน้าไหน (ลิงก์กระโดดได้)
3. เล่าเป็นเรื่องเดียวต่อเนื่อง ร้านสมมติ 1 ร้าน ผ่านวันทำงาน 1 วัน
4. มีปุ่มรีเซ็ต Demo กลับจุดเริ่มต้นได้ทุกเมื่อภายใน 1 คลิก
5. ห้ามใช้ mock ตัวเลขบนหน้า Demo ทุกตัวเลขต้องมาจาก API จริงตัวเดียวกับที่ระบบใช้งานปกติ

### ข้อกำหนดอื่นที่ได้รับในบทสนทนาเดียวกัน (สรุปความ ไม่ใช่คำต่อคำ)

โครงสร้างของเอกสารแผน ต้องมีหัวข้อ A ถึง H เรียงตามนี้

- A Persona และเรื่องเล่า ชื่อร้าน สินค้า **8 ถึง 12 รายการ** (ใช้ของที่มีใน seed ถ้าเหมาะ) ลูกค้าขายส่ง **2 ถึง 3 ราย** ระดับราคา 3 ระดับ role ที่จะสาธิต
- B สถานะข้อมูลเริ่มต้น T0 ล็อตต้นทุนของแต่ละสินค้า สต็อกคงเหลือ และตัวเลข Dashboard ก่อนเริ่ม
- C ตาราง Scene ทีละ step แต่ละแถวต้องมี **7 คอลัมน์** คือ ลำดับ / หน้าที่อยู่ / สิ่งที่ user กด / ผลบนหน้าจอพร้อม before และ after ที่คำนวณไว้ล่วงหน้าจริง / data flow ว่าตารางไหนถูกเขียน / feature ที่กระทบพร้อมลิงก์ / ข้อความอธิบายบน UI ไม่เกิน 2 ประโยค ภาษาชาวบ้าน
  ต้องครอบคลุมอย่างน้อย: รับของเข้า 2 ล็อตคนละต้นทุน, Import Shopee, จับคู่ SKU ที่ยังไม่รู้จักและสินค้าชุด, Import Lazada ที่มีแถวเสีย, Import TikTok, Import ไฟล์เดิมซ้ำแล้วต้องไม่ตัดซ้ำ, ไฟล์ใหม่ที่มีออเดอร์ยกเลิกแล้วสต็อกกลับ, เปิดบิลขายส่งเลือกลูกค้าแล้วราคาเปลี่ยนตามระดับ, ออก PDF, ยกเลิกบิล, ดูประวัติสต็อกและ Dashboard, ดูรายงานกำไร, สลับ role เป็นพนักงานแล้วดูหน้าเดิมทั้งหมด
- D **ฉาก FIFO 103,400 บาท** ต้องอยู่ในเรื่องเล่า และมี step ที่ให้เห็นการไล่ล็อตทีละล็อตว่าทำไมได้เลขนี้
- E UX ของกลไก Guided Tour เลือกรูปแบบ ระบุ component ที่จะสร้าง state ที่เก็บ วิธี highlight ปุ่มข้าม ย้อน รีเซ็ต และพฤติกรรมเมื่อ user ออกนอกเส้นทาง (ไม่บังคับ แต่ชี้ทางกลับ)
- F Demo assets ที่ต้องสร้าง ไฟล์ export 3 แพลตฟอร์ม ระบุแถวเสีย ออเดอร์ซ้ำ ออเดอร์ยกเลิกที่ต้องแฝงไว้ seed เพิ่มเติม และข้อความบน UI ทั้งหมด
- G Gap list feature ที่ยังไม่มีและกระทบ Demo พร้อมเสนอว่าจะทำเพิ่มขั้นต่ำ ตัดออก หรือต้องรอ พร้อมประเมินขนาดงาน
- H แผน implement Phase 2 ลำดับงาน ไฟล์ที่จะแตะ acceptance test

- สรุปคำถามที่ต้องการให้ตัดสินใจ **ไม่เกิน 5 ข้อ** แล้วหยุดรอคำว่า "อนุมัติ"

### งานที่ 2

ไม่มีส่วนต่าง แผนตรงกับโค้ดจริงทุกจุด
`DbExecutor` (`packages/db/src/client.ts:105`) มี `execute` และ `insert` ครบพอดีตามที่ `seedDatabase` ต้องใช้
export ออกทาง `packages/db/src/index.ts` แทนการเพิ่ม subpath `./seed` ใน `package.json` เพราะ `exports` ปัจจุบันมีแค่ `.`, `./schema`, `./repositories`

ระหว่างทางเจอ `bun run db:seed` ล้มครั้งหนึ่งด้วย socket error ของ postgres แล้วทำให้เทสตกตามมา 8 ตัว
รันซ้ำแล้วปกติ ไม่ใช่ปัญหาของโค้ด แต่เป็นอีกเหตุผลที่ต้องดูผล seed ก่อนตีความผลเทสเสมอ

### งานที่ 3

**ส่วนต่างที่ 1 - `apps/api/src/routes/index.ts` เป็น barrel จริง แต่ต้องแก้ทั้งสองที่**

ผู้ตรวจรอบ 2 บอกว่าจุดต่อ router จริงคือ `apps/api/src/index.ts:42-54` และ `routes/index.ts` เป็นแค่ barrel ซึ่งถูกต้อง
แต่ต้องแก้ **ทั้งสองไฟล์** คือ export ใน barrel แล้วค่อย `.route('/demo', demoRouter)` ใน `index.ts` ไม่ใช่แก้ไฟล์เดียว

**ส่วนต่างที่ 2 - เทสต้องใช้ path เต็ม `/api/v1/...`**

`buildTestApp` (`apps/api/src/test-utils.ts`) ต่อ v1 ไว้ใต้ `app.route('/api/v1', v1)`
เทสที่เรียก `/demo/reset` ตรงๆ จะได้ 404 ทุกครั้ง และที่อันตรายคือ **เทส "ต้องได้ 404" จะผ่านแบบหลอก**
ตอนแรกผมเขียนผิดแบบนี้จริง ผลคือ 1 ผ่าน 3 ตก โดยตัวที่ "ผ่าน" คือตัวที่ไม่มีความหมาย
บทเรียน: เทสที่ยืนยันสถานะ error ต้องมีเทสคู่กันที่ยืนยันเส้นทางสำเร็จ ไม่งั้นแยกไม่ออกว่า 404 มาจาก logic หรือมาจาก path ผิด

**ส่วนต่างที่ 3 - กั้นด้วย `development` อย่างเดียว ไม่รวม `test`**

`testEnv` ตั้ง `ENVIRONMENT: 'test'` ตอนแรกผมใส่ `'test'` เข้าไปในรายการที่รีเซ็ตได้เพื่อให้เทสผ่านง่าย
แล้วตัดออก เพราะทุกค่าที่เพิ่มในรายการนี้คือช่องทางทำข้อมูลหายเพิ่มอีกหนึ่งช่อง
เทสส่งค่า `'development'` เข้ามาเองผ่านพารามิเตอร์ `env` ที่เพิ่งเพิ่มให้ `requestAs` แทน

**ตัวแปรใหม่ที่ต้องตั้ง: `DATABASE_URL_DEMO`**

เทสของ endpoint นี้ต้องชี้ไปฐานข้อมูลที่สอง ถ้าไม่ตั้ง เทสจะข้ามทั้งชุดเหมือนเทส DB ตัวอื่น
คำสั่งสร้างอยู่ใน Preflight P12 ต้องบันทึกใน `apps/api/README.md` ตอนงานที่ 12

**ผลลัพธ์ของงานที่ 3**

- `bun test apps/api/src/routes/demo.test.ts` ผ่าน 4/4
- `bun test` เต็ม **272 ผ่าน 0 ตก** และรันซ้ำทันทีโดยไม่ re-seed ก็ยังได้ 272/0 พิสูจน์ว่าเทสใหม่ไม่ทิ้งขยะไว้
